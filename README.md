# نظام إدارة حلقات تحفيظ القرآن الكريم

نظام ويب متكامل لإدارة حلقات تحفيظ القرآن في المسجد: الطلاب، المعلمون، الحلقات، الحضور، التسميع اليومي،
الاختبارات المتسلسلة، طلبات النقل والإيقاف، بوابة أولياء الأمور، الدعم الفني، الإشعارات والمحادثات الفورية.

الواجهة عربية بالكامل باتجاه RTL ومتجاوبة مع الجوال والأجهزة اللوحية وسطح المكتب.

## التقنيات

### الخادم (Backend)

| التقنية | الاستخدام |
|---|---|
| NestJS 10 + TypeScript | إطار العمل وبنية الوحدات |
| Prisma 5 | ORM والهجرات (Migrations) |
| PostgreSQL 14+ | قاعدة البيانات |
| JWT + Passport | المصادقة (رمز وصول + رمز تجديد) |
| Socket.IO | المحادثات والإشعارات الفورية |
| Swagger / OpenAPI | توثيق الواجهة |
| class-validator | التحقق من المدخلات |
| bcryptjs + helmet | تشفير كلمات المرور وحماية الترويسات |

### الواجهة (Frontend)

| التقنية | الاستخدام |
|---|---|
| React 18 + TypeScript | واجهة المستخدم |
| Vite 5 | أداة البناء وخادم التطوير |
| React Router 6 | التنقل وحماية المسارات |
| TanStack Query 5 | جلب البيانات والتخزين المؤقت |
| Zustand | حالة المصادقة |
| Axios | عميل HTTP مع تجديد الرمز تلقائياً |
| Tailwind CSS 3 | التنسيق ونظام التصميم |
| Recharts | الرسوم البيانية |
| Socket.IO Client | الاتصال الفوري |

> **ملاحظة عن قاعدة البيانات:** يستخدم المشروع **PostgreSQL** لأنه المتوفر والمثبّت على بيئة التطوير الحالية
> (لم يكن MySQL مثبتاً). للتحويل إلى MySQL: غيّر `provider` في `backend/prisma/schema.prisma` إلى `"mysql"`،
> واستبدل حقول `String[]` (مثل `Circle.scheduleDays`) بحقل نصي أو جدول منفصل لأن MySQL لا يدعم المصفوفات،
> ثم أعد توليد الهجرات.

## التثبيت السريع

من مجلد المشروع الرئيسي:

```bash
# 1) أنشئ قاعدة البيانات (مرة واحدة)
psql -U postgres -c "CREATE DATABASE quran_circles;"

# 2) اضبط بيانات الاتصال
#    انسخ backend/.env.example إلى backend/.env وعدّل DATABASE_URL

# 3) تثبيت الحزم + الهجرات + البيانات التجريبية
npm run setup
```

ثم شغّل الخادمين في نافذتي طرفية منفصلتين:

```bash
npm run dev:backend    # http://localhost:3000
npm run dev:frontend   # http://localhost:5173
```

افتح المتصفح على **http://localhost:5173** وسجّل الدخول بالبريد `admin@alnoor-quran.sa` وكلمة المرور `Pass@1234`.

## التثبيت خطوة بخطوة

### 1. قاعدة البيانات

```bash
psql -U postgres -c "CREATE DATABASE quran_circles;"
```

على ويندوز إذا لم يكن `psql` في مسار النظام:

```powershell
& "C:\Program Files\PostgreSQL\14\bin\psql.exe" -U postgres -c "CREATE DATABASE quran_circles;"
```

### 2. الخادم

```bash
cd backend
cp .env.example .env      # على ويندوز: copy .env.example .env
```

عدّل `DATABASE_URL` في `backend/.env` ليطابق بيانات اتصالك:

```env
DATABASE_URL="postgresql://postgres:YOUR_PASSWORD@localhost:5432/quran_circles?schema=public"
```

ثم:

```bash
npm install
npm run prisma:migrate    # ينشئ الجداول
npm run seed              # يعبّئ البيانات التجريبية
npm run dev               # http://localhost:3000
```

### 3. الواجهة

في نافذة طرفية جديدة:

```bash
cd frontend
npm install
npm run dev               # http://localhost:5173
```

خادم التطوير يمرّر `‎/api` و `‎/uploads` و `‎/socket.io` تلقائياً إلى الخادم على المنفذ 3000،
لذلك لا حاجة لضبط CORS أثناء التطوير.

## الحسابات التجريبية

كلمة المرور موحّدة لجميع الحسابات: **`Pass@1234`**

تسجيل الدخول يتم **باسم المستخدم**. البريد الإلكتروني بيانات تواصل اختيارية ولم يعد وسيلة دخول،
ويمكن إنشاء حساب بدونه تماماً.

| الدور | اسم المستخدم | ما يراه |
|---|---|---|
| مدير عام | `admin` | كل شيء: المستخدمون، الحلقات، الدورات، الكادر، الإعلانات، اعتماد الطلبات |
| مشرف | `supervisor1` / `supervisor2` | حلقاته المسندة إليه وحلقته الخاصة إن وُجدت |
| معلم | `teacher1` … `teacher7` | حلقاته وطلابه، الحضور، التسميع، التحضير، طلبات النقل/الإيقاف/الاختبار، وقائمة أولياء الأمور لربط طالب جديد |
| لجنة اختبارات | `committee1` / `committee2` | قائمة الانتظار والجدولة ورصد النتائج **فقط** |
| ولي أمر | `parent1` … `parent12` | أبناؤه فقط (قراءة فقط) |
| دعم فني | `support` | تذاكر الدعم والرد عليها |

> شاشة الدخول **لا تعرض هذه الحسابات**. كانت تعرضها لتسهيل الاستكشاف، وهو ما لا مكان له في نظام
> يُستخدم فعلاً — فالجدول أعلاه للتوثيق وحده، ويختفي أثره تماماً بعد `npm run db:fresh`.

**قواعد اسم المستخدم:** حروف إنجليزية فقط، أو أرقام فقط، أو مزيج منهما (3–32 حرفاً).
يُسمح بـ `.` و`_` و`-` كفاصل بين الأجزاء لا في البداية أو النهاية. لا يُطلب أي مزيج إجباري
من الحروف والأرقام والرموز.

أي حساب ينشئه المدير لاحقاً يبدأ بكلمة مرور تعيّنها الإدارة، ويُوجَّه صاحبه عند أول دخول إلى صفحة
**الملف الشخصي** لتغييرها قبل استخدام أي شاشة أخرى.

البيانات التجريبية تشمل: ٦ حلقات، ٧ معلمين، ٧١ طالباً (منهم ٦ في الدورات فقط و٢ في برنامج النشاط)،
١٢ ولي أمر، ٤ دورات تعليمية مع تسجيلاتها وحضورها، أكثر من ١١٠٠ سجل حضور للطلاب و١١٧ للكادر،
نحو ٤٠٠ سجل تسميع بنقاطها، ١٥٤ سورة مكتملة، تكاليف تحضير، ٣ إعلانات،
٦٠ مقرر اختبار (الأحزاب الستون)، اختبارات ناجحة وراسبة وقائمة انتظار،
طلبات نقل وإيقاف، تذاكر دعم، ومحادثات فردية وجماعية.

### أول تشغيل في مدرسة حقيقية

البيانات التجريبية أعلاه للاستكشاف فقط. للبدء بنظام نظيف:

```bash
npm run db:wipe       # يفرّغ كل جدول، ثم يضع الحد الأدنى اللازم للتشغيل
# أو على قاعدة فارغة أصلاً:
npm run bootstrap
```

`db:wipe` يفرّغ **كل الجداول** (`TRUNCATE ... RESTART IDENTITY CASCADE`) ويحذف الملفات المرفوعة
من `UPLOAD_DIR`، ثم يعيد بناء الحد الأدنى. المخطّط وسجل الهجرات يبقيان كما هما — فهو تفريغ بيانات
لا إعادة تنصيب، ولا يحتاج قاعدة ظل ولا إعادة تشغيل كل هجرة.

| | |
|---|---|
| يُحذف | كل شيء: المستخدمون، الطلاب، الحلقات، الحضور، التسميع، الاختبارات، المحادثات، الملفات المرفوعة |
| يبقى | مخطّط قاعدة البيانات وسجل الهجرات |
| يُنشأ | ٦٠ حزباً (مقررات الاختبارات) + صف إعدادات المدرسة + **مستخدم واحد** |

الملفات المرفوعة تُحذف لأن الصفوف التي تشير إليها تُحذف؛ لإبقائها:
`npm run db:wipe -- --keep-uploads`.

> السكربت يطبع ما سيُحذف ثم **يرفض التنفيذ بلا `--force`**، وسكربت npm هو الذي يمرّرها —
> فلا يمكن أن يُشغَّل بالخطأ.

كلاهما ينتهي إلى الشيء نفسه: **حساب واحد فقط** — المدير العام — ومعه صف إعدادات المدرسة
ومقررات الاختبارات الستين (بيانات مرجعية لا تجريبية). لا طلاب ولا حلقات ولا حسابات اختبار.

| | |
|---|---|
| اسم المستخدم | `admin1` |
| كلمة المرور | `admin@2026` |

يمكن تغييرها بمتغيرات البيئة `ADMIN_USERNAME` و`ADMIN_PASSWORD` و`ADMIN_NAME`.

> **غيّر كلمة المرور بعد أول دخول.** لا يجبرك النظام على ذلك: من يعيّن كلمة مرور — لنفسه أو
> لغيره — مؤتمن على اختيارها، فالحسابات هنا تُسلَّم باليد لا بالبريد.

السكربت **لا يفعل شيئاً إذا كانت قاعدة البيانات تحتوي أي حساب**، فتشغيله مرتين أو على نظام
قيد الاستخدام لا يمكن أن يطمس أحداً.

## الأدوار والصلاحيات

النظام يطبّق مستويين من الحماية:

1. **حماية على مستوى الدور** — `RolesGuard` عام يمنع الوصول لنقاط النهاية غير المسموحة للدور.
2. **حماية على مستوى المورد** — `AccessControlService` يحدد *أي* الحلقات والطلاب يستطيع هذا المستخدم بالذات رؤيتهم أو تعديلهم.

| الدور | النطاق |
|---|---|
| **مدير عام** | وصول كامل لكل الوحدات، واعتماد جميع الطلبات |
| **مشرف** | الحلقات المسندة إليه فقط: طلابها، معلموها، حضورها، تسميعها، اختباراتها |
| **معلم** | حلقاته فقط (أساسي أو مساعد). يسجّل الحضور والتسميع والتقييم، ويقدّم طلبات النقل والإيقاف والاختبار |
| **لجنة اختبارات** | وحدة الاختبارات فقط: قائمة الانتظار والجدولة ورصد النتائج. **لا تصل** إلى صفحات الطلاب أو المعلمين أو الحلقات |
| **ولي أمر** | أبناؤه فقط، **قراءة فقط**، وطلبات الدعم الخاصة به |
| **دعم فني** | تذاكر الدعم فقط، ولا يصل لبيانات الطلاب |

**المشرف قد يكون معلماً أيضاً:** يجوز إسناد حلقة خاصة به إلى جانب إشرافه على حلقات أخرى.
`AccessControlService.ownCircleIds` يوحّد المجموعتين، فلا يُسأل المشرف "هل أنت معلم هنا أم مشرف؟"
— وصفحة **المشرفون** تعرض العمودين منفصلين.

**أمثلة مطبّقة فعلياً في الخادم:**

- المعلم لا يستطيع فتح ملف طالب خارج حلقاته → `403`
- ولي الأمر لا يستطيع رؤية طالب آخر → `403`
- المعلم يستطيع تعديل بيانات التواصل ومستوى الحفظ فقط، ومحاولة تعديل الاسم أو الهوية أو الحلقة تُرفض → `403`
- المشرف لا يستطيع تعيين مشرف أو معلم أساسي (صلاحية إدارية) → `400`
- إيقاف حساب أو حذفه يُلغي جميع جلساته فوراً

> الواجهة تُخفي ما لا يملكه المستخدم، لكن **القرار النهائي دائماً في الخادم** — إخفاء الزر ليس حماية.

## ملاحظات الواجهة

### القائمة الجانبية القابلة للطي

على الشاشات الكبيرة يمكن طي القائمة الجانبية إلى شريط أيقونات (٨٠ بكسل بدلاً من ٢٨٨) بالضغط على زر
السهم في الشريط العلوي. عند الطي تظهر تلميحات عند مرور المؤشر، وتتحول عدادات الإشعارات إلى نقاط صغيرة.
الحالة تُحفظ في `localStorage` تحت المفتاح `qc.sidebarCollapsed` فتبقى بين الجلسات.
على الجوال لا ينطبق الطي — القائمة تظهر كدرج منسدل كامل.

### الأرقام والتواريخ داخل نص عربي (`.numeric`)

النصوص المختلطة (أرقام لاتينية داخل فقرة عربية) تنعكس بصرياً إذا تُركت لخوارزمية الاتجاه الافتراضية،
فيظهر التاريخ `2026/08/14` على شكل `142026/08/`. لذلك يوفّر النظام صنف `.numeric`:

```css
.numeric {
  font-variant-numeric: tabular-nums;
  unicode-bidi: plaintext;   /* يحدد الاتجاه من أول حرف قوي في المحتوى */
  white-space: nowrap;
}
```

استخدمه على أي تاريخ أو رقم أو رمز أو رقم جوال. **لا تُضِف إليه `display` أبداً** — الصنف يُطبَّق على
عناصر `<td>`، وأي تغيير في `display` يُخرج الخلية من تخطيط الجدول ويُفقد محاذاة الأعمدة.

### الحضور: يُحفظ مرة واحدة ثم يُصحَّح من السجل

بعد حفظ كشف حضور حلقة في يوم معيّن **يختفي النموذج بالكامل** وتظهر مكانه رسالة
«تم حفظ كشف الحضور لهذا اليوم» مع زر ينقل إلى سجل الحضور. لا استثناء لأحد: يرفض الخادم أي إرسال
ثانٍ لنفس (الحلقة، التاريخ) — حتى من المدير العام — لأن التصحيح له طريق واحد.

**التصحيح يتم من سجل الحضور، طالباً طالباً**: يُفتح اليوم ثم الحلقة، فتظهر حالات كل طالب كأزرار
قابلة للتغيير مباشرة عبر `PATCH /api/attendance/:id`. الصلاحية نفسها المطلوبة لتسجيل الكشف
(`assertCircleWriteAccess`)، وأي تحويل إلى «غياب بدون عذر» يُشعِر ولي الأمر كما لو سُجِّل ابتداءً.

سبب الفصل بين الأمرين: الكشف اليومي عملية جماعية تُقفل بمجرد إتمامها، بينما التصحيح واقعة مفردة
تخصّ طالباً بعينه — وخلطهما كان يسمح بإعادة كتابة يوم كامل من أجل تعديل صفّ واحد.

الحالات ثلاث لا رابع لها: **حاضر**، **غياب بعذر** (مع حقل السبب)، **غياب بدون عذر**. نسبة الحضور
تُحتسب من الحاضرين فقط.

### الجداول

- الخلايا لا تلتف افتراضياً (`white-space: nowrap`) ليبقى ارتفاع الصفوف متساوياً.
- للأعمدة النصية الطويلة (مثل «السبب») أضف `whitespace-normal` على الخلية.
- `.table` لها `min-width: 44rem` فتُمرَّر أفقياً داخل `.table-wrap` على الشاشات الضيقة بدل ضغط الأعمدة.
- المحاذاة موروثة من `.table`، لذا تبقى أدوات مثل `text-center` على خلية بعينها فعّالة.

## قاعدة البيانات

النموذج يغطي ٢٣ جدولاً. أهم العلاقات:

- **`User`** هو الحساب. المعلم وولي الأمر لهما ملف إضافي (`TeacherProfile` / `ParentProfile`) بعلاقة ١:١.
- **`CircleTeacher`** يربط المعلم بالحلقة بدور (`PRIMARY` / `ASSISTANT`). الحقل `endedAt = null` يعني الإسناد الحالي،
  وبقية السجلات تشكّل **تاريخ الإسناد الكامل** — لا يُحذف شيء عند النقل.
- **`CircleMembership`** يفعل الشيء نفسه للطلاب: كل انتقال بين الحلقات يُغلق سجلاً ويفتح آخر.
- **`StudentEvaluation`** يحفظ تاريخ كل تغيير في التقييم اليدوي، بينما يحتفظ `Student.evaluation` بالقيمة الحالية.
- **`Attendance`** عليه قيد فريد `(studentId, date)` — إعادة تسجيل نفس اليوم تُحدّث السجل ولا تكرره.
  الحالات ثلاث فقط: `PRESENT` (حاضر) و`EXCUSED` (غياب بعذر) و`ABSENT` (غياب بدون عذر)، والحقل `note`
  يحمل سبب العذر ولا يُحفظ إلا مع `EXCUSED`.
- **`Recitation`** للتسميع اليومي: تقييم عام (`evaluation`) وملاحظات فقط — بلا درجة رقمية وبلا عدد أخطاء.
- **`Exam`** للاختبار الرسمي: `score` من 100 وهو ما يحدّد النجاح، و`mistakes` **اختياري**، و`notes` للملاحظات.
- **`SuspensionRequest`** و **`TransferRequest`** تحفظان الطلب وقراره ومنفّذه، مع الاحتفاظ بالسجل بعد التنفيذ.
- **الحذف الناعم** (`deletedAt`) مطبّق على المستخدمين والمعلمين وأولياء الأمور والطلاب والحلقات والتسميع والتذاكر والملاحظات.

**الفهارس:** أُضيفت فهارس على كل حقول التصفية والفرز المستخدمة فعلياً — حالة الطالب، الحلقة، التاريخ،
حالة الطلب، مالك الإشعار، ومحادثة الرسالة — لتظل الاستعلامات سريعة مع آلاف السجلات.

لاستعراض البيانات بصرياً:

```bash
cd backend && npm run prisma:studio
```

## قاعدة بيانات سحابية (Neon / Supabase)

النظام يعمل على PostgreSQL محلي أو مُستضاف دون أي تغيير في الشيفرة. الفرق الوحيد أن المزوّدين
السحابيين يقدّمون **نقطتَي اتصال**، ولكل منهما دور:

| المتغير | النقطة | الاستخدام |
|---|---|---|
| `DATABASE_URL` | المجمّعة (pooled) | التطبيق أثناء التشغيل |
| `DIRECT_URL` | المباشرة (direct) | `prisma migrate` فقط |

**لماذا؟** المجمِّع (PgBouncer) يعمل في وضع المعاملات، ولا يوفّر جلسة حقيقية، بينما تحتاج
Prisma Migrate إلى قفل استشاري (advisory lock) وإلى تنفيذ DDL داخل جلسة واحدة. تشغيل الترحيلات
عبر النقطة المجمّعة هو السبب الأشيع لفشل الإعداد على قاعدة سحابية.

على Neon: العنوان المباشر هو نفسه بعد حذف `-pooler` من اسم المضيف.

```bash
# backend/.env
DATABASE_URL="postgresql://user:pass@ep-xxx-pooler.us-east-2.aws.neon.tech/neondb?sslmode=require&pgbouncer=true&connect_timeout=20"
DIRECT_URL="postgresql://user:pass@ep-xxx.us-east-2.aws.neon.tech/neondb?sslmode=require&connect_timeout=20"
```

ثم التهيئة الكاملة (ترحيلات + بيانات تجريبية):

```bash
npm run db:setup
```

### ملاحظات عملية

- **`channel_binding=require`** الذي ينسخه Neon في نصّ الاتصال يجب حذفه؛ مشغّل Prisma لا يدعم
  SCRAM channel binding.
- **`pgbouncer=true`** على النقطة المجمّعة يوقف الاستعلامات المُحضَّرة (prepared statements)
  التي لا يدعمها المجمِّع.
- **خطأ `P1002 … pg_advisory_lock`**: نقطة Neon المجانية تنام عند الخمول، وأول اتصال يوقظها
  فينتهي وقت القفل. شغّل الأمر مرة أخرى بعد إيقاظها، أو مرّر:
  ```bash
  PRISMA_SCHEMA_DISABLE_ADVISORY_LOCK=true npm run db:setup
  ```
- **البطء طبيعي**: كل استعلام يقطع مسافة إلى مركز البيانات. الاستخدام العادي سلس، لكن
  السكربتات التي تنفّذ مئات الطلبات المتتابعة تصبح أبطأ بعشرات المرّات مقارنة بقاعدة محلية.
- **نسخة Prisma مثبّتة في المشروع** (`5.22.0`) وتُستدعى من `backend/node_modules`؛ لا حاجة
  لتثبيت Prisma عالمياً ولا لترقيته.

## نظام الاختبارات: بالحزب، بالتسلسل، وفي اتجاه الحلقة

المسار كله **٦٠ حزباً** (`ExamSection` بنوع `HIZB`، بالحقل `order` من ١ إلى ٦٠). الحزب هو الوحدة
التي تختبر بها الحلقة فعلياً، ولذلك **لا تُطلب الأجزاء ولا تظهر في نافذة الطلب**؛ والجزء يُشتقّ
للعرض فقط: كل حزبين = جزء (`juzFromHizb` في `backend/src/common/quran.ts`).

### الاتجاه ثم التسلسل

للحلقة أن تبدأ من أي طرف:

- **تصاعدياً** من الحزب ١ إلى الحزب ٦٠، أو
- **تنازلياً** من الحزب ٦٠ إلى الحزب ١.

ما دام الطالب لم يجتز شيئاً بعد فالطرفان معاً متاحان، ولا شيء بينهما. أول حزب يجتازه **يحدّد
الاتجاه**، ومن بعده يمشي المسار بالتسلسل: الحزب التالي هو الذي يلي آخر ما اجتازه.

**والاختبار الواحد قد يغطي أكثر من حزب متتالٍ**: من كان نازلاً من ٦٠ يستطيع طلب ٥٧ و٥٦ و٥٥ في
اختبار واحد — بشرط أن يكون ٦٠ و٥٩ و٥٨ خلفه بالفعل. لا يجوز القفز ولا ترك فجوة داخل الطلب نفسه.

```
لا شيء مُجتاز  →  الحزب 1  أو  الحزب 60          (الطرفان فقط)
اجتاز 60       →  الاتجاه = تنازلي، التالي: 59
اجتاز 60,59,58 →  يُقبل طلب [57] أو [57,56] أو [57,56,55]
               →  يُرفض طلب [55] وحده، ويُرفض [57,55] لوجود فجوة
```

التحقق يتم على **المجموعة كاملة** لا على كل حزب وحده (`assertSequential`)، لأن معنى «هل هذا هو
التالي؟» يتوقف على بقية ما في الطلب نفسه. ويُحفظ الأدنى ترتيباً كمقرر أساسي
(`ExamRequest.sectionId`) بينما تُحفظ المجموعة كاملة في `exam_request_sections`
و`exam_sections_on_exams`.

```
طلب الاختبار (معلم) — حزب أو أكثر متتالٍ في اتجاه الطالب
   ↓  التحقق: لم يُجتَز، ولا طلب قائم عليه، وهو التالي في المسار
قائمة الانتظار PENDING
   ↓  اللجنة تجدول
اختبار مجدول SCHEDULED  →  إشعار للمعلم وولي الأمر والممتحن
   ↓  رصد النتيجة
COMPLETED  →  PASSED إذا كانت الدرجة ≥ درجة النجاح، وإلا FAILED
              (الدرجة من 100 إلزامية، وعدد الأخطاء اختياري)
   ↓  عند النجاح: تُحدَّث الأجزاء المحفوظة = عدد الأحزاب المجتازة ÷ ٢
```

- **الاختبار الواحد يُرصد على كل أحزابه**: النجاح في اختبار يغطي أربعة أحزاب يجعل الأربعة مجتازة،
  لا مقرره الأساسي وحده. القراءة تجمع `Exam.sectionId` مع جدول `exam_sections_on_exams` في كل
  موضع: الأهلية، والتسلسل، وحساب الأجزاء المحفوظة.
- **الأجزاء المحفوظة كسرية**: `memorizedParts` عدد عشري = الأحزاب المجتازة ÷ ٢، فخمسة أحزاب تساوي
  ٢٫٥ جزء. كانت عدداً صحيحاً، فكان اجتياز حزب واحد يُقرأ صفراً وشريط التقدّم يبقى فارغاً.
- الرسوب لا يُغلق شيئاً: يعيد المعلم تقديم الطلب لنفس الحزب.
- **الطلب القائم يحجز كل أحزابه**، لا مقرره الأساسي وحده، فلا يمكن طلب حزب هو أصلاً ضمن طلب معلّق.
- **كل رسالة وشاشة تذكر الأحزاب كاملة**: اختبار من الحزب ١ إلى ٥ يُكتب «الأحزاب ١ إلى ٥ (٥ أحزاب)»
  في نموذج الممتحن، وقائمة اللجنة، وإشعار المعلم، وإشعار ولي الأمر — لا «الحزب ١» وحده.
  الصياغة من `describeSections` في الخادم و`describeExamSections` في الواجهة، ليقول الطرفان الشيء نفسه.
- شاشة الطالب تعرض المسار بأربع حالات: **مجتاز** (أخضر)، **طلب قائم** (أزرق)، **متاح الآن** (ذهبي)،
  **مغلق حتى اجتياز ما قبله** (رمادي).
- نافذة الطلب تعرض الاتجاه أولاً (إن لم يكن محسوماً)، ثم الأحزاب بالترتيب: النقر على حزب يأخذه وما
  قبله، والنقر على آخر حزب مأخوذ يتراجع عنه — فلا يمكن أصلاً تكوين مجموعة غير متتالية.
- `GET /api/exams/eligibility/:studentId` يعيد `direction` و`chains`: المسار المتبقّي مرتّباً،
  ومنه تبني الواجهة كل ما سبق.
- الأجزاء الثلاثون **لم تُحذف** من قاعدة البيانات: هجرة `20260826120000_exams_by_hizb` تجعلها
  `isActive = false` فقط، فتظل الاختبارات والطلبات القديمة تعرض مقرّرها الصحيح، ولا يمكن طلب
  مقرر جديد عليها.
- لتغيير المنهج: عدّل `HIZB_SECTIONS` في `backend/src/common/quran.ts` وفي `backend/prisma/seed.ts`،
  أو أضف مقررات من واجهة الإدارة عبر `POST /api/exams/sections`.

## ما الذي يميّز هذا الإصدار

### إيقاف الطالب: ثلاثة قرارات

يرفع المعلم **سبب الطلب فقط**، وتختار الإدارة القرار:

| القرار | الأثر على الطالب | الحلقة | المدة |
|---|---|---|---|
| التحويل لبرنامج النشاط | `ACTIVITY` | يخرج منها | بلا مدة |
| إيقاف مؤقت | `SUSPENDED` | يبقى فيها | بالأيام |
| **إيقاف نهائي** | `WITHDRAWN` | يخرج منها | بلا مدة، ولا عودة تلقائية |

الإيقاف النهائي ينهي تسجيل الطالب في المدرسة ويبقي ملفه كاملاً في السجل الموحّد. لا يعود إلا
بإجراء «إعادة إلى حلقة» من الإدارة.

**برنامج النشاط يعني «خارج كل الحلقات»** — وهذا شرط تحفظه قاعدة البيانات نفسها
(`students_activity_has_no_circle`)، لا الخدمة وحدها: تحويل الطالب من نموذج التعديل يُخرجه من
حلقته ويُغلق عضويته، وإسناده لحلقة وهو في البرنامج مرفوض. وله أن يشارك في **الدورات** بلا مانع —
فالدورة ليست حلقة.

### السجل الموحّد للطلاب

> **من يراه:** السجل الموحّد للإدارة والمشرفين فقط. المعلم يفتح الصفحة نفسها فيجدها باسم
> «طلاب حلقاتي» بلا مرشّحات المسارات، لأن نطاقه أصلاً طلاب حلقاته (`studentScope`) — فلا معنى
> لعرض إطار يَعِد بمدرسة كاملة.

سجل واحد يضم **كل من دخل المدرسة**: طلاب الحلقات، وطلاب الدورات، والمحوَّلون إلى برنامج النشاط،
والموقوفون. لا توجد جداول منفصلة لكل فئة — بل `Student` واحد مع مرشّحات مسار:

| المسار | المعنى |
|---|---|
| حلقات التحفيظ | مسجّل في حلقة وحالته `ACTIVE` |
| الدورات التعليمية | له تسجيل قائم في دورة (وقد يكون في حلقة أيضاً) |
| برنامج النشاط | `ACTIVITY` — خارج الحلقات وما زال في السجل |
| الموقوفون | `SUSPENDED` — باقٍ في حلقته مع مدة إيقاف |

هذا التداخل هو سبب وجود السجل الموحّد: الطالب قد يكون في حلقة ودورة معاً، وإخفاؤه من إحدى
القائمتين لأنه ظاهر في الأخرى هو ما كان يجعل الصفحات المنفصلة تتناقض.

### برنامج النشاط مقابل الإيقاف

مُقدّم الطلب يذكر **السبب فقط**. الإدارة هي من تقرر:

| القرار | الأثر |
|---|---|
| **التحويل إلى برنامج النشاط** | يخرج من الحلقة، يبقى في السجل، بلا مدة محددة. للطالب الذي لا يقرأ بعد أو صغير السن أو يحتاج تهيئة |
| **الإيقاف** | يبقى في حلقته، حالته «موقوف»، بمدة تحددها الإدارة |
| **الرفض** | يبقى منتظماً |

وكذلك **طلب النقل**: مُقدّم الطلب يذكر السبب، والإدارة تختار الحلقة الجديدة عند الاعتماد —
لأن اختيار الحلقة قرار إسناد يعتمد على السعة والمستوى.

### نظام النقاط

| العنصر | القيمة |
|---|---|
| كل آية مُسمّعة | **+1** |
| كل خطأ | **−1** |
| كل تنبيه | **−0.25** |
| إتمام سورة | **+10** (قابلة للتعديل) |

- عدد الآيات يُحتسب تلقائياً من نطاق التسميع، ويمكن للمعلم تجاوزه.
- الجلسة لا تنزل تحت الصفر: من يتعثّر لا يخسر نقاطاً كسبها في أيام أخرى.
- `students.totalPoints` مخزّن كذاكرة مؤقتة ويُعاد حسابه بالكامل عند أي تعديل أو حذف،
  فلا ينحرف عن مجموع سجلاته.
- المصدر الوحيد للقاعدة: `backend/src/common/points.ts`، وتُعرض النتيجة مباشرة في نموذج التسميع.

### الدورات التعليمية

مسار مستقل تماماً عن حلقات التحفيظ: جداوله وتسجيلاته وحضوره في جداول منفصلة
(`courses`, `course_enrollments`, `course_attendance`)، فلا يختلط سجل دورة بسجل حلقة.
النوعان: **دورات شرعية** و**أحكام التجويد**. المحاضر إما حساب في النظام أو اسم خارجي.

### الكادر

- **دليل موحّد** يجمع المعلمين والمشرفين والإداريين ولجنة الاختبارات والدعم في قائمة واحدة،
  مع عمود واحد للحلقات يجمع الإسناد كمعلم والإشراف معاً.
- **حضور الكادر** بنفس منطق حضور الطلاب: كشف يومي، ثلاث حالات، إرسال واحد ينتقل بعده إلى السجل.

### الإعلانات

تنشرها الإدارة وحدها. `audience` فارغ يعني الجميع، وإلا فالأدوار المحددة فقط.

**الوجهة نوعان**، يختارهما المدير من النموذج:

| النوع | المثال | السلوك عند الضغط |
|---|---|---|
| صفحة داخل النظام | `/courses` | تنقّل داخلي عبر الموجّه |
| رابط خارجي | `https://example.org/news` | يُفتح في **تبويب جديد** ويبقى النظام مفتوحاً كما هو |

الرابط الخارجي يُفتح بـ `noopener,noreferrer` حتى لا تستطيع الصفحة المفتوحة التحكم بالتبويب
الأصلي عبر `window.opener`. والتحقق في `CreateAnnouncementDto` يقبل **المسار الداخلي** أو
**`http(s)://`** فقط، ويرفض `javascript:` و`data:` والشكل النسبي `//host` — الإعلان رابط تضغطه
المدرسة كلها، فالتحقق حدٌّ أمني لا زينة.

### صورة الطالب

الطالب لا يملك حساباً، فصورته على السجل نفسه (`Student.photoUrl`) لا على مستخدم. يضعها **ولي الأمر
من بوابته** — وهو صاحب صورة ابنه فعلاً — أو الكادر من ملف الطالب، عبر
`PATCH /api/students/:id/photo`. الصلاحية من `assertStudentAccess`: ولي الأمر لأبنائه وحدهم،
والكادر لمن يراهم أصلاً. والصورة المستبدلة تُحذف من التخزين كبقية الصور.

**الرابط الداخلي يُعرض لمن يستطيع فتحه فقط.** الإعلان الواحد يخاطب عدة أدوار — «افتُتحت دورة
جديدة» تخص المدرسة كلها — لكن الصفحة خلفه قد لا تكون متاحة لهم جميعاً: `/courses` ليس لولي الأمر
فيها مسار، وضغط «عرض التفاصيل» كان يقذفه إلى «لا تملك صلاحية الوصول». الآن **يبقى الإعلان كما هو
ويسقط الرابط وحده**: لا زر تفاصيل، ولا عنوان قابل للضغط. الفحص في `canOpenPath`
(`src/config/navigation.tsx`) مشتق من جدول التنقّل نفسه، فلا يوجد جدول صلاحيات ثانٍ يتباعد عنه.

ونموذج النشر يقول ذلك للمدير مقدّماً: كل صفحة في القائمة موسومة بالفئات التي لا تملكها، ويظهر
تنبيه عند التعارض — فيختار صفحة أخرى، أو رابطاً خارجياً، أو يحصر الفئات المستهدفة. التنبيه
إرشادي لا مانع؛ النشر يبقى قرار المدير.

**الإخفاء يخصّ صاحبه:** مفتاح `qc.dismissedAnnouncements.<userId>` في `localStorage`، لأن جهاز
المكتب الواحد يتناوب عليه المدير والمعلمون وأولياء الأمور — وإخفاء أحدهم لإعلان يجب ألا يخفيه عمّن
يدخل بعده.

> **ذاكرة الاستعلامات عند تبديل الحساب:** `queryClient.clear()` يُستدعى عند الدخول والخروج
> (`src/lib/queryClient.ts`). بدونه يرث الحساب الجديد ما حمّله السابق في التبويب نفسه: أول ما ظهر
> ذلك أن ولي أمر دخل بعد المدير فلم يرَ إعلاناً موجّهاً لأولياء الأمور، لأن القائمة المحفوظة كانت
> قائمة المدير — والمسألة أوسع من الإعلانات، إذ تشمل كل بيانات محدودة بالدور.

### قيود المحادثات

| الدور | يستطيع مراسلة |
|---|---|
| مدير عام / دعم فني | الجميع |
| معلم / مشرف | الكادر + أولياء أمور طلاب حلقاته فقط |
| لجنة اختبارات | الكادر فقط |
| ولي أمر | الإدارة + معلمي ومشرفي حلقات أبنائه فقط |

**ولي الأمر لا يستطيع مراسلة ولي أمر آخر**، ولا يستطيع أي دور الوصول إلى *كل* أولياء الأمور.
القواعد في `AccessControlService.contactableUserFilter`، ويستخدمها كل من دليل المراسلة
وإنشاء المحادثة، فلا يمكن أن يتباعدا.

### الجلسة والخروج التلقائي

لا يوجد حدث متصفح موثوق لـ«تم الإغلاق» (`beforeunload` يُطلق عند التحديث أيضاً، ولا يُطلق عند
إنهاء التبويب). لذلك يكتب التبويب المفتوح نبضة كل ٥ ثوانٍ في `localStorage`؛ وعند الإقلاع، إن كانت
الفجوة منذ آخر نبضة **أكثر من دقيقة** فهذا يعني أن المتصفح كان مغلقاً فعلاً، فتُمسح الجلسة قبل
استخدامها. التحديث أو فتح رابط في تبويب جديد ينتج فجوة بالمللي ثانية ولا يتأثر.

### رفع الصور

`UploadsService` يرفع إلى **Cloudinary** عند وجود بياناتها في `.env`، ويحفظ محلياً في `UPLOAD_DIR`
عند غيابها — فالمدرسة التي لم تشترك في Cloudinary تستطيع رفع شعار وصور شخصية كالمعتاد.
واجهة Cloudinary تُستدعى عبر REST مباشرة (توقيع SHA-1 وطلب واحد) دون إضافة أي حزمة جديدة.

```bash
# backend/.env — اختياري
CLOUDINARY_CLOUD_NAME=
CLOUDINARY_API_KEY=
CLOUDINARY_API_SECRET=

# مطلوب: العنوان المطلق لواجهة الخادم، وتُبنى عليه روابط الصور
PUBLIC_URL=http://localhost:3000
```

> **ملاحظة على مسار الشعار:** كانت الروابط تُخزَّن كـ `/uploads/x.png`، والمتصفح يحلّها على أصل
> الواجهة (خادم Vite على المنفذ 5173) لا على الخادم، فتظهر مكسورة. صار الخادم يعيد عنواناً مطلقاً،
> ويُعاد بناء أي مسار قديم نسبيّ على `PUBLIC_URL` عند القراءة.

**الحذف:** أي صورة تُستبدل أو تُزال تُحذف من التخزين فعلياً — من Cloudinary عبر `image/destroy`،
ومن القرص عبر `unlink` — في `UploadsService.remove` / `removeIfReplaced`. تُستدعى تلقائياً عند
تغيير الصورة الشخصية (`PATCH /auth/profile` و`PATCH /users/:id`) وعند استبدال شعار المدرسة أو
إزالته، وهناك `DELETE /api/uploads` لصورة رُفعت ثم صُرف النظر عنها قبل الحفظ. الحذف **أفضل جهد**:
فشله يُسجَّل في السجلّ ولا يُفشل العملية التي استدعته، ومسار الملف المحلي يُقيَّد داخل مجلد الرفع
فلا يمكن لرابط مصنوع أن يخرج منه.

**العرض:** الصور الشخصية دائرية بـ `object-cover` داخل إطار ثابت، وتعود إلى الأحرف الأولى إذا فشل
تحميل الملف (`onError`) بدل ترك أيقونة الصورة المكسورة. النقر على الصورة يفتحها بملء الشاشة
(`Lightbox` عبر `createPortal` حتى لا تُقصّ داخل بطاقة أو خلية جدول).

**الشعار** ليس مربعاً بطبيعته ولا يوضع على لوح أبيض: يُعرض بارتفاع ثابت وعرض حرّ
(`object-contain`) مباشرة على خلفية الشاشة في صفحة الدخول والشريط الجانبي — فالشعار ذو الخلفية
الشفافة يجب أن يذوب في الخلفية لا أن يجلس داخل مربع. الاستثناء الوحيد معاينة صفحة الإعدادات:
خلفيتها مربّعات رمادية فاتحة ليميّز المدير بين شعار شفاف وآخر أبيض قبل النشر.

### الحذف الجماعي: بطلب لا بشكل دائم

مربعات الاختيار لا تظهر في الجداول افتراضياً. الزر «حذف جماعي» في رأس الصفحة هو ما يُظهرها، ومعه
شريط فيه «تحديد الكل» وعدّاد المحدد وزر الحذف، و«إنهاء التحديد» يخفيها ويمسح ما اختير. المنطق كله
في `useBulkSelect` + `<BulkBar>`، ويستعمله الطلاب والمستخدمون والدورات بالسلوك نفسه.

### الدعم الفني من صفحة الدخول

من لا يستطيع الدخول هو أحوج الناس للدعم، لذا زر التواصل متاح **قبل** تسجيل الدخول.
الطلب يُنشئ تذكرة بلا صاحب مع بيانات تواصل، ومحدود بـ **٣ طلبات لكل جهاز في الساعة**.
ولي الأمر يرى **طلباته هو فقط** ولا يستطيع تصفح طلبات غيره.

التذكرة القادمة من صفحة الدخول **بلا صاحب حساب** (`createdById = null`) وتحمل بيانات تواصل بدلاً
منه، فتُعرض باسم المُرسِل مع وسم «من صفحة الدخول». أي شاشة تعرض مُقدّم الطلب تمرّ عبر
`ticketRequesterName` بدل قراءة `createdBy.fullName` مباشرة — فقراءتها مباشرةً كانت تُسقط لوحة
معلومات حساب الدعم الفني بالكامل إلى صفحة بيضاء.

## الإشعارات والمحادثات الفورية

Socket.IO مستخدم **حصراً** للمحادثات والإشعارات اللحظية. كل ما عدا ذلك يمرّ عبر REST.

- **المسار:** `/socket.io` — **النطاق (namespace):** `/realtime`
- **المصادقة:** يُرسل رمز الوصول في `auth.token` أثناء المصافحة (handshake)، ويُرفض الاتصال إذا كان الرمز غير صالح أو الحساب موقوفاً.
- **الغرف:** `user:<id>` للإشعارات الشخصية، `conversation:<id>` للمحادثات، `role:<ROLE>` للبث حسب الدور.

| الحدث | الاتجاه | الوصف |
|---|---|---|
| `notification:new` | خادم ← عميل | إشعار جديد + عدد غير المقروء |
| `chat:message` | خادم ← عميل | رسالة جديدة في محادثة مفتوحة |
| `chat:inbox` | خادم ← عميل | تنبيه لعضو خارج المحادثة المفتوحة |
| `chat:read` / `chat:message-deleted` | خادم ← عميل | تحديث حالة القراءة / حذف رسالة |
| `presence:update` | خادم ← عميل | اتصال/انقطاع مستخدم |
| `typing` | ثنائي الاتجاه | مؤشر «يكتب الآن» |
| `conversation:join` / `conversation:leave` | عميل ← خادم | الانضمام لغرفة محادثة (يُتحقق من العضوية) |

**الإشعارات تُحفظ في قاعدة البيانات** مع حالة مقروء/غير مقروء، فلا تضيع إذا كان المستخدم غير متصل.
وإذا كان عضو المحادثة غير متصل يُنشأ له إشعار دائم بالرسالة.

### إدارة المحادثات والمجموعات

| الإجراء | من يملكه |
|---|---|
| تعديل رسالة | كاتب الرسالة فقط، وتُوسم «مُعدَّلة» |
| حذف رسالة | كاتبها، أو مشرف المجموعة (إشراف)، أو المدير العام |
| عرض الأعضاء | أي عضو في المجموعة |
| إضافة أعضاء | مشرف المجموعة |
| ترقية عضو / إزالة الإشراف | مشرف المجموعة |
| إزالة عضو | مشرف المجموعة |
| تعديل الاسم والوصف | مشرف المجموعة |
| **الإرسال للمشرفين فقط** | مشرف المجموعة — يبقى الأعضاء قادرين على القراءة |
| **إغلاق المجموعة** | مشرف المجموعة — إيقاف الرسائل نهائياً مع حفظ السجل |
| مغادرة المجموعة | أي عضو (لا تنطبق على المحادثات الفردية) |

- مُنشئ المجموعة يصبح مشرفها تلقائياً، ولا يمكن أن تبقى المجموعة دون مشرف واحد على الأقل.
- تُرجع الواجهة الخلفية الحقول `isAdmin` و `canPost` و `isClosed` و `adminOnly` مع كل محادثة،
  فتُخفي الواجهة الأمامية محرّر الرسائل وأزرار الإدارة بناءً عليها بدل إظهار أزرار تفشل عند الضغط.
- قيود المجموعات لا تنطبق على المحادثات الفردية؛ محاولة تطبيقها عليها تُرفض بـ `400`.

الأحداث التي تولّد إشعارات: قرارات النقل والإيقاف، جدولة الاختبارات ونتائجها، طلبات الاختبار الجديدة،
ردود الدعم الفني، رسائل المحادثات، تسجيل الغياب (لولي الأمر)، وإسناد الحلقات.

## النشر للإنتاج

### 1. تجهيز البيئة

```bash
# على الخادم
export NODE_ENV=production
export DATABASE_URL="postgresql://user:strong_password@db-host:5432/quran_circles?schema=public"
export JWT_ACCESS_SECRET="$(openssl rand -hex 32)"
export JWT_REFRESH_SECRET="$(openssl rand -hex 32)"
export CORS_ORIGINS="https://your-domain.com"
export PORT=3000
```

> **مهم:** لا تستخدم القيم الافتراضية لمفاتيح JWT في الإنتاج إطلاقاً، ولا ترفع ملف `.env` إلى المستودع.

### 2. بناء وتشغيل الخادم

```bash
cd backend
npm ci --omit=dev
npx prisma generate
npx prisma migrate deploy      # يطبّق الهجرات دون إنشاء هجرات جديدة
npm run build
node dist/main.js
```

للتشغيل الدائم عبر PM2:

```bash
npm install -g pm2
pm2 start dist/main.js --name quran-api --env production
pm2 save && pm2 startup
```

### 3. بناء الواجهة

```bash
cd frontend
npm ci
npm run build                  # الناتج في frontend/dist
```

ارفع محتويات `frontend/dist` إلى أي خادم ملفات ثابتة (Nginx، Apache، Netlify، Vercel…).

### 4. مثال إعداد Nginx

```nginx
server {
    listen 80;
    server_name your-domain.com;

    # ملفات الواجهة الثابتة
    root /var/www/quran-circles/dist;
    index index.html;

    # مسارات React Router تُعاد إلى index.html
    location / {
        try_files $uri $uri/ /index.html;
    }

    # واجهة API
    location /api/ {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    # الملفات المرفوعة (الشعار)
    location /uploads/ {
        proxy_pass http://127.0.0.1:3000;
    }

    # Socket.IO — يحتاج ترقية الاتصال إلى WebSocket
    location /socket.io/ {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_set_header Host $host;
        proxy_read_timeout 86400;
    }
}
```

## استكشاف الأخطاء

**`Can't reach database server` عند تشغيل الهجرات**
تأكد أن خدمة PostgreSQL تعمل وأن `DATABASE_URL` صحيح:
```bash
pg_isready -h localhost -p 5432
```

**`password authentication failed for user "postgres"`**
كلمة المرور في `DATABASE_URL` غير مطابقة. عدّل `backend/.env`.

**الواجهة تعمل لكن كل الطلبات ترجع `401`**
انتهت صلاحية الجلسة. سجّل الخروج والدخول مجدداً. إذا تكرر ذلك بعد إعادة تشغيل الخادم فالسبب أن
`JWT_ACCESS_SECRET` تغيّر — الرموز القديمة لم تعد صالحة، وهذا سلوك صحيح.

**`الحلقة مكتملة العدد` عند نقل طالب**
سعة الحلقة الهدف ممتلئة. ارفع `capacity` من صفحة الحلقة أو اختر حلقة أخرى.

**المحادثات لا تصل فورياً**
تحقق من وصول `/socket.io` إلى الخادم. خلف وسيط (proxy) يجب تمرير ترويسات `Upgrade` و `Connection`
كما في مثال Nginx أعلاه. النظام يعمل بدون WebSocket لكن الرسائل ستتأخر حتى التحديث التالي.

**`لا يمكن طلب هذه الأحزاب قبل اجتياز "الحزب ٥٨"`**
الأحزاب تُطلب بالتسلسل في اتجاه الطالب. اطلب التالي في المسار، أو ضُمّ إليه ما يليه. راجع
[نظام الاختبارات](#نظام-الاختبارات-بالحزب-بالتسلسل-وفي-اتجاه-الحلقة).

**`تم حفظ كشف حضور هذه الحلقة لهذا اليوم، ويمكن تعديل حضور أي طالب من سجل الحضور`**
هذا ليس خطأ — الكشف يُرسل مرة واحدة. لتعديل حالة طالب افتح **سجل الحضور** ← اليوم ← الحلقة.

**`لا يمكن حذف الحلقة لوجود طلاب مسجلين بها`**
انقل الطلاب إلى حلقة أخرى أولاً، ثم احذف الحلقة.

**منفذ ٣٠٠٠ أو ٥١٧٣ مشغول**
غيّر `PORT` في `backend/.env`، أو `server.port` في `frontend/vite.config.ts`.
