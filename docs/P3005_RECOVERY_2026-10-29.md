# استعادة الخدمة عند P3005

أكدت سجلات Render أن `migrate deploy` توقف لأن قاعدة الإنتاج ليست فارغة ولا يوجد سجل ترحيلات معتمد. وجود أخطاء P2022 سابقاً يثبت أن المخطط لا يطابق كامل الترحيلات. لذلك لا يجوز تسجيل الترحيلات الـ41 كلها كمطبقة.

## استعادة الخدمة الحالية

1. أنشئ نسخة احتياطية أو فرع استعادة في Neon، وتأكد من اختيار قاعدة وفرع التطبيق الصحيحين.
2. نفّذ كامل الملف `backend/prisma/recovery/add-personal-leave-and-push-channel.sql` في Neon SQL Editor. يجمع تغييرَي `20261025000000_push_notification_sound` و`20261028200000_self_absence_period` في معاملة واحدة، ويقبل إعادة التنفيذ مع إبقاء التواريخ المسجلة. لا يحذف طلبات أو أجهزة ولا يسجل baseline.
3. تأكد من نجاح COMMIT وظهور الحقول الأربعة في الاستعلام الأخير. إذا فشل أي أمر، توقّف ولا تشغّل بقية الأوامر منفردة؛ المعاملة تتراجع عن التغييرات.
4. مؤقتاً، أعد Start Command في Render إلى `node dist/main.js` ثم أعد النشر. هذا مسار تشغيل مباشر للمخطط المُصلح يدوياً، وليس حلاً لسجل الترحيلات.
5. تحقق من صحة API وفتح صفحة أذونات الغياب، وأن أخطاء P2022 للأعمدة المذكورة اختفت. لا تثبت هذه الخطوات اكتمال بقية مخطط الإنتاج.

## إصلاح سجل الترحيلات لاحقاً

استخرج المخطط الحالي وسجل `_prisma_migrations` إن وجد، وقارنه بتاريخ الترحيلات في قاعدة اختبار مستعادة من النسخة الاحتياطية. راجع الفروق قبل إنشاء baseline خاص بالحالة الفعلية. لا تستخدم `migrate resolve --applied` لجميع الترحيلات دون هذه المقارنة. بعد معالجة السجل واختبار `migrate deploy` على النسخة المستعادة، يمكن العودة إلى `npm run start:prod`.

السجل المعروض يشير إلى عنوان Neon يحتوي `-pooler`. اضبط `DIRECT_URL` من رابط الاتصال المباشر في لوحة Neon لأوامر الترحيل، مع إبقاء `DATABASE_URL` للتشغيل. هذا لا يعالج P3005 وحده.

لم يُنفذ ملف الإصلاح على الإنتاج من هذه الجلسة، ولم تُختبر المعاملة على قاعدة PostgreSQL متاحة محلياً. موصل Render لا يدعم تنفيذ SQL على Neon أو تعديل Start Command.
